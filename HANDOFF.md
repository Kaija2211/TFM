### B. The font-crispness investigation and fix (`3610f37`) — see [[project_oswald_bold_font_fix]]

Thomas reported UI text looking blurry, starting with the Title screen. This took a genuinely long live-diagnosis arc: ruled out (with hard evidence each time, not assumption) Canvas Scaler fractional scaling from a non-16:9 Game View, Windows display scaling (Thomas checked, was 100%), a "baked texture upscaled" theory raised by a design collaborator (checked Camera.targetTexture, Canvas.renderMode, RawImage usage, render pipeline — all ruled out), before finding the real cause: `Oswald SDF.asset` was baked from a single weight of the variable `Oswald-Variable.ttf`, with no true bold face — every `FontStyles.Bold` label (most of the UI) was rendering through TMP's synthetic faux-bold simulation, not real glyphs, which is well-known to look soft on numerals at small sizes.

Fixed by downloading the genuine static `Oswald-Bold.ttf` (Google Fonts, OFL-licensed, explicit permission given before downloading), baking a matching `Oswald Bold SDF` TMP asset at identical atlas settings, and linking it into the existing font's weight table — this makes the fix automatic and global (every label already goes through the same default font asset), not something requiring per-screen patching. **A real mistake was caught and fixed mid-task**: the first attempt at creating the bold font asset didn't persist its atlas texture/material as sub-assets, so it worked in-session but threw `MissingReferenceException` the moment Play Mode actually transitioned — caught by testing through a real transition rather than trusting the first success, then fixed properly. Verified comprehensively: 246 unique bold labels audited live across every major screen, zero still on faux-bold.

## 4. Gotchas learned this session (save yourself the rediscovery time)

- **`NormalizeButtonLabel`/`SetDisabledPlaceholder`/`StyleHubActionButton` only ever update an existing label, they never create one.** Any brand-new code-built button needs an explicit `ManagerUITheme.BuildLabel(...)` call first. See [[feedback_normalizebuttonlabel_needs_existing_label]].
- **The TMP cached-label gotcha struck a third time** — see [[feedback_tmp_cached_label_reference_gotcha]]. Cache the parent GameObject, not the `TextMeshProUGUI`, for any label built with empty starting text.
- **`GetOverallRating()` is a weighted average, not a sum** — spreading a growth/development amount across many attributes barely moves it. Add the intended delta directly to the attributes that actually carry weight for a given position instead.
- **Unity's `TrueTypeFontImporter` doesn't expose variable-font weight/instance selection** — importing a single variable `.ttf` only ever gives you one weight (whatever the font's default instance is), not a way to select others from the same file. A genuinely different static weight file is needed for a real bold/light/etc. face.
- **`TMP_FontAsset.CreateFontAsset` doesn't automatically persist its generated atlas texture/material as sub-assets** — you must explicitly `AssetDatabase.AddObjectToAsset` both, or the font asset works in-session but throws `MissingReferenceException` on the next Play Mode transition once the orphaned in-memory objects get garbage-collected.
- **`AssetDatabase.DeleteAsset` and `File.Delete` inside `Application.persistentDataPath` both hit "User interactions are not supported" in this sandboxed `Unity_RunCommand` environment** — use the Bash/shell tool for file deletion instead when a mistake needs cleaning up.
- **Editing C# scripts while still in Play Mode is unreliable** (already known, reconfirmed) — a burst of unrelated `TMP_SubMeshUI` NullReferenceExceptions appeared mid-edit, fully resolved by exiting and re-entering Play Mode fresh. Always force a clean exit/re-enter cycle before trusting a live verification.
- **Rapid, same-frame automated testing (chaining many screen transitions in one script call with no real elapsed time) can show stale/doubled state that isn't a real bug** — Unity's `Destroy()` is deferred to end-of-frame, and this Editor session doesn't always tick a frame between rapid same-call transitions. If a live check shows implausible-looking duplication, re-check after a genuinely separate tool call (real elapsed time) before concluding it's a real bug.
- Carried forward, still true: `Unity_RunCommand` script edits sometimes need an actual Play Mode restart to take effect; no true save/load existed before this session (now fixed, but AI-club squads still don't persist by design); the `Random.State` save/restore technique remains the standard for any future `AgentSquadGenerator.cs` addition.
