### Bugs found and fixed via live testing (roughly chronological)
- **Ghost/ orphaned scene objects resurfacing**: a stray "Make Sub" button and a stray "Player Details" text label — both leftover `GameObject`s from before this redesign whose C# field references had been deleted, but the scene objects themselves never were. Found via scene-YAML fileID tracing, surgically removed.
- **Formation dropdown misaligned** with the Formation button after the header rework — stale position, one-line fix.
- **Scroll direction wrong on Match Events and the new Squad List** — see the dedicated section below, this took multiple rounds to actually nail down.
- **Matchday Prep opponent list rendering grey/white** — its ScrollView's background `Image` had never been recolored because the screen used to stay permanently hidden before this redesign; now that it's shown, Unity's default light-grey sprite was showing through.
- **Match Day live header "juju"** — team names/score/clock were overflowing past the header's own bottom divider because `headerHeight` was still at its pre-redesign value (110) while the score/clock fonts had grown significantly. Also found and fixed a **second, more serious latent copy of the same bug**: `ResetMatchStatsPanelToLiveLayout` (runs on every single match) had its own separate stale header-height constant, silently resetting the stats panel to the wrong position on *every* match, not just the first.
- **Team names going blank at Full-Time** — the classic documented TMP mesh-generation-failure bug (`characterCount=0` despite the text being correctly set), this time triggered by a `fontSize` change on an *already-rendered* label rather than at creation, which is a new trigger case worth remembering. Fixed with a dedicated recovery coroutine that (unlike the existing generic sweep helper) also reassigns the class-level field to the recreated component, since these two labels get their `.text` reassigned again on every subsequent match.
- **Full-Time goal-scorer list overflowing past the top border** when there are 3+ goals — was positioned inside the header, right under the score; moved below the header entirely, with Match Stats pushed down to make room.

### The second, much longer live-testing round (this is where most of the real bugs were)
The user did their own hands-on pass after the first round of fixes and came back with a fresh list. Several of these took more than one attempt to actually get right:

- **Hub league table sizing "fix" silently never took effect.** `LeagueTableView`'s `rowHeight`/`headerRowHeight`/`fontSize` are `[SerializeField]` fields on an Editor-placed component — the *scene file* has its own baked values (28/22/13) that override whatever the C# field defaults say. My first attempt only edited the C# defaults and had **zero effect** at runtime. Had to edit the `.unity` scene file's serialized MonoBehaviour data directly (now 48/32/20). **Worth remembering generally**: any `[SerializeField]` on an Editor-placed (not code-instantiated) component needs its *scene-serialized* value checked/edited, not just the C# default — the C# default only applies to freshly-created instances.
- **Hub table column spacing** — PL/GD/PTS were right-aligned in wide columns, leaving a big dead gap on the near side of each column and making the FORM column look squeezed against GD. Switched those three to center-aligned instead.
- **Form column letters ("W D L") don't line up consistently** — proportional font means "W" is wider than "L"/"D", so the space-joined string doesn't read at an even rhythm. Fixed with TMP's `<mspace=1.4em>` tag around the whole string, forcing every character (letters and the join-space) to the same fixed advance width.
- **GK pin sitting on the pitch's bottom edge** — reverted from 0.95 back to the source mockup's own 0.90 now that the canvas is native 1920x1080 (0.95 was a compensation for the old cramped 960x540-derived canvas that no longer applies).
- **GK/CB pin overlap specifically on the three back-three formations** (3-5-2, 3-4-3, 3-4-2-1) — their center CB sits deeper than the side CBs by design (0.80 vs 0.76), which combined with the GK's corrected 0.90 left almost no gap. Nudged the center CB to 0.74.
- **Player Detail banner** — went through three rounds: (1) centered the stat columns to close a big empty gap below them, which just relocated the gap to *above* the stats instead; (2) grew the banner itself (130→240px, bigger photo/name/meta) to actually consume the space; (3) user pointed out the banner didn't fill the screen *horizontally* either — it had the same centered-1600px-region margin as the stat grid below it; removed that margin so the banner is full-bleed while the stats stay centered.
- **Weak-foot star alignment** — this took **three separate correction rounds**, each verified live, because I was eyeballing pixel offsets in screenshots instead of measuring. Finally solved properly by querying `TMP_TextInfo.characterInfo` directly for a plain x-height letter ('o') vs. the star sprite's own bounding box — turned out the star artwork itself sits well below its own reported baseline, so no amount of `voffset` baseline-matching was ever going to work. Computed the exact center-to-center gap (6.49 units at fontSize 21 ≈ 0.31em) and landed on `voffset=0.29em` (up from an initial guess of `-0.15em`), verified to within 0.02 units via direct measurement, not a screenshot glance.
- **Scroll direction, settled for real this time.** This flip-flopped across three rounds (+1 → -1 → back to +1) because early attempts were based on user reports against **stale Play Mode sessions** (see the dedicated section below) rather than the actual current build. Finally settled by simulating an actual wheel-scroll event via `ExecuteEvents.Execute(..., ExecuteEvents.scrollHandler)` and directly reading `ScrollRect.verticalNormalizedPosition` before/after — proved unambiguously that `+1` (Unity's own default) is correct; `-1` tries to push the list toward the top even when scrolling down. Applied to both Match Events and the Squad List View.
- **Matchday Prep "pitch is behind the list" — NOT a z-order bug, a real position bug.** Reported as recurring even after earlier fixes. Turned out both the pitch and list overlap-check-worthy earlier "fix" (ghost text + GK position) never actually addressed the real cause. Measured via `RectTransform.GetWorldCorners` and found the list's right edge sat **149 units past** the pitch's left edge, at the exact window size the user was testing in (not maximized/fullscreen). Root cause: `CanvasScaler`'s effective canvas width only equals the 1920 reference when the window's aspect ratio is exactly 16:9 — in the user's actual (narrower) window it measured **2117.42 units wide**, not 1920. The squad list was already positioned as an offset *from the right anchor*, which happens to be aspect-ratio-independent by construction; the pitch was positioned as a fixed distance *from the left edge*, computed using a literal `1920f`, which is not. Re-anchored the pitch (and its "OPPONENT SHAPE" caption) from the right edge the same way the list already was, and its height from the container's actual measured `.rect.height` instead of a literal `1080f`. Verified with a **positive 27.75-unit gap** at the same window size that previously showed the ~149-unit overlap.
- **Pitch markings barely visible in a non-maximized window** — `BuildPitchMarkings`' halfway line and penalty box lines were declared at a literal 1px width against the 1920x1080 reference. Whenever the actual window is smaller than reference resolution (i.e. not maximized), that 1 reference-pixel scales down to *less than* one real screen pixel and anti-aliases away to nearly nothing, especially combined with their already-low 10% opacity. Bumped every pitch-marking line from 1px to 2px.

### A recurring meta-problem: chrome-build-once + no save system
Nearly every screen's UI is built exactly once per Play Mode session (`Build*Chrome()` guarded by a bool) and never rebuilt. This means:
- Scene-file-level fixes (deleted ghost objects, `[SerializeField]` value changes) **do not** take effect in an already-running Play Mode session — only a fresh Play Mode entry picks them up.
- Several "still broken!" reports from the user turned out to be against a session that had been running continuously since *before* the relevant fix landed — not the fix actually being wrong. This wasted real time on at least the scroll-direction issue (see above) before I recognized the pattern.
- There's no save/load system yet (`LOAD CAREER (SOON)` is still a disabled placeholder), so a Play Mode restart **discards all season progress**. Mid-session, the user was 39 matchdays into a season when this was discovered — did **not** restart Play Mode without asking, waited for the user to stop it themselves before verifying the next round of fixes.

**Takeaway for next time**: if the user reports a fix "still" not working, the first question should be "did you restart Play Mode since that fix landed?" before assuming the fix itself is wrong.

## 4. Gotchas learned this session (save yourself the rediscovery time)

- **`[SerializeField]` fields on Editor-placed (not code-instantiated) components can have scene-baked values that silently override the C# field default.** Editing the C# default alone has zero runtime effect if the scene file already has a concrete serialized value for that field. Check/edit the `.unity` file's serialized MonoBehaviour data directly when this is suspected (symptom: a numeric/style tweak that "should" have worked visibly didn't).
- **TMP's mesh-generation-failure bug can be triggered by a `fontSize` (or other property) change on an *already-rendered* label, not just at creation.** The previously-documented trigger was "freshly `AddComponent`'d this frame" — this session found a new case: bumping `fontSize` on a long-lived label (team names, live→full-time transition) hit the identical `characterCount=0`-despite-correct-text symptom. Same destroy+recreate fix applies, but reassign any class-level field pointing at the label, since the generic sweep helper doesn't do that and a label whose `.text` gets set again next match will throw if the field still points at a destroyed component.
- **Don't eyeball pixel alignment from a screenshot when you can measure it.** The star-alignment saga took three extra rounds because early attempts adjusted `<voffset>` based on how it *looked* zoomed into a screenshot. Querying `TMP_TextInfo.characterInfo[i].bottomLeft`/`.topRight` directly (via `Unity_RunCommand`) for both the reference glyph and the sprite, and computing the exact required offset, got it right in one shot once actually used. The same applies to overlap/z-order-looking bugs: `RectTransform.GetWorldCorners()` on the two suspect elements settles it in one call instead of guessing from a screenshot.
- **`ScrollRect.scrollSensitivity`'s correct sign is not a matter of taste or hardware-dependent guessing — it's directly testable.** Simulate a wheel event with `ExecuteEvents.Execute(target, pointerEventData, ExecuteEvents.scrollHandler)` (with `eventData.scrollDelta` set to the direction being tested) and read `verticalNormalizedPosition` before/after. `+1` (Unity's default) is very likely always correct for a standard content list; if a report says otherwise, suspect a stale Play Mode session (see section 2) before flipping the sign again.
- **`CanvasScaler`'s effective canvas width/height only equals the reference resolution when the window's aspect ratio exactly matches it.** Any UI positioning math using a literal reference-resolution constant (e.g. `1920f`, `1080f`) instead of the actual container's `RectTransform.rect.width`/`.height` will silently drift whenever the window isn't that exact aspect ratio (i.e. essentially always, in a resizable/non-maximized window). Symptoms can look like z-order bugs (two elements that should be adjacent instead overlap) even though there's no sibling-order problem at all — always check actual measured positions before assuming z-order. Positioning something as an *offset from the far anchor edge* (like `offsetMax` on a stretched rect) is aspect-ratio-safe by construction; a fixed distance from the *near* edge via `anchoredPosition` on a point-anchor is not, unless the anchor itself is on the far edge too.
- **A literal 1px-wide/tall `Image` used as a hairline (pitch markings, dividers) can vanish below the reference resolution.** If the actual window is smaller than the `CanvasScaler` reference resolution, 1 reference-pixel scales to less than 1 real screen pixel and anti-aliases away — worse at low opacity. Use at least 2px for anything meant to stay visibly present at less-than-reference window sizes.
- **Chrome-build-once (`Build*Chrome()` guarded by a bool, run once at `Start()`/first-open) means neither code fixes nor scene-file fixes apply to an already-running Play Mode session.** Every verification this session needed a genuine Play Mode stop+restart, not just a script recompile (domain reload alone reruns methods with new code but doesn't rebuild already-constructed screens). Confirm with the user whether they've restarted since a fix landed before trusting a "still broken" report at face value.
- **There is no save/load system yet** — restarting Play Mode discards all in-progress season state. Never restart Play Mode without checking whether the user has progress they care about first; wait for them to stop it themselves if unsure.
- **`Unity_RunCommand` requires the exact shape** `internal class CommandScript : IRunCommand { public void Execute(ExecutionResult result) { ... } }` — top-level statements produce a `CS8805` compile error. `System.Reflection` is blocked inside these scripts. `ScreenCapture.CaptureScreenshot(path)` captures the actual Game view (screen-space Canvas UI); `Unity_Camera_Capture`/Scene View tools do not and are useless for this kind of UI verification.
- Carried forward, still true: `Destroy()` makes a `UnityEngine.Object` compare `== null` immediately despite deferred actual destruction; Unity's MCP/RunCommand tooling occasionally needs a full Play Mode restart to clear stale state ("Unity not detected" errors that resolve on retry); `Image` needs full qualification (`UnityEngine.UI.Image`) inside `Unity_RunCommand` scripts.
