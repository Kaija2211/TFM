## 2. Part 1: `potentialemails.txt` Tier 1 batch (14 templates) + retirement (15th, ad hoc)

All wired directly into `ManagerPrototypeController.cs` as inline `inbox.Add(...)` calls at the natural trigger point for each, following the same inline-body-string convention `ManagerTransferNegotiation`/`ManagerScouting` already established (no separate template file). `InboxMessageType` enum (`Manager/Save/ManagerSaveData.cs`) extended with 11 new values — purely a display tag today, same as the original three (`RefreshInboxUI` doesn't branch on `Type` yet).

- **Welcome / Season Expectations / Recruitment Teaser** (#1, #2, #30) — all three land together the moment `OnConfirmTeamClicked` actually starts a new career (not on load/return-to-hub, which also calls `ShowSeasonHub`). New `SendCareerStartInboxMessages()`.
- **Post-match reaction** (#6-10, win/big win/draw/loss/heavy loss) — new `SendPostMatchReactionForManagedTeam`, called from `ApplyFixtureResult`. **Explicit gating decision** (the session 13 handoff flagged this as open): a notable result (`|margin| >= 3`) always sends immediately; an ordinary win/draw/loss only sends once `PostMatchReactionMinGapMatchdays = 2` matchdays have passed since the last one, to avoid a message after literally every one of 38 fixtures.
- **Form streak pair** (#11/#12, poor run / strong run) — new `CheckFormStreakMessages`, reads the existing `recentFormByTeamId` Form-strip history. Fires once when a 3-result streak (`FormStreakLength`) first forms, not on every match still inside it (a `poorRunMessageSentForCurrentStreak`/`strongRunMessageSentForCurrentStreak` flag pair, reset the moment the streak breaks).
- **Low-stamina warning** (#18) — new check inside `ResolveMatchdayInboxTicks` (see part 6.5), fires when any squad player's `ManagerSquadRoles.GetCondition` drops under `LowStaminaWarningThreshold = 60`, cooldown-gated (`LowStaminaWarningCooldownMatchdays = 5`) so a long fatigued stretch doesn't repeat every matchday.
- **Mid-season review** (#27) — same `ResolveMatchdayInboxTicks`, fires once when `currentFixtureIndex >= managedTeamFixtures.Count / 2`.
- **End-of-season success/disappointment** (#28/#29) — added to `ApplySeasonEndRewards`. Cutoff: top-half-of-table finish reads as success, bottom-half as disappointment (simple, since there's no "expected finish" concept in this prototype to compare against instead). Reused the existing `GetOrdinalSuffix` helper — first pass duplicated it as a private method with a different signature and hit a genuine `CS0111` compile error, caught immediately via `Unity_GetConsoleLogs` and fixed by deleting the duplicate.
- **Retirement** (Thomas's mid-session addition, not in `potentialemails.txt`) — added inside `ApplyRetirementsForTeam`, managed-team-only (an AI club's retirements are invisible replacements today, nothing to tell the manager about), one message per retiree at season rollover.

**Frequency-gating call worth a second look**: the post-match reaction 2-matchday gap and the low-stamina 5-matchday cooldown were both picked as reasonable defaults, not validated against a real playthrough. If Thomas finds the Inbox too quiet or too noisy once he's actually played a season against it, those two constants are the first thing to retune.

## 3. Part 2: Playtest backlog (Tactics Board + interaction fixes)

All in `ManagerPrototypeController.cs` unless noted.

- **Auto-Pick hidden mid-match** — `autoPickButton` promoted from a local var to a field, toggled `SetActive(!tacticsBoardOpenedMidMatch)` in `RefreshTacticsBoardUI` (the panel is shared chrome between the pre-match Tactics Board and the mid-match Make Changes flow, built once).
- **Bidirectional Squad drag** (`TacticsBoardPlayerCard.cs`) — root cause: pins were `isDraggable: true, isDropTarget: true` but bench cards were `isDropTarget: false`, so `OnDrop`'s branch (which used `isDropTarget` as a stand-in for "is this a pin") silently did nothing when a pin was dropped onto a bench card. Fixed by adding an explicit `isPinCard` identity flag separate from `isDropTarget`, making bench cards drop targets too (with `OnBenchPlayerDroppedOnPin` now wired instead of `null`), and rewriting `OnDrop`'s branch to cover all four drag-direction combinations — a pin dropped on a bench card now calls the same substitution callback with the arguments reversed, which is semantically identical to the already-working bench-onto-pin direction.
- **Injury cross on the Tactics Board's own bench card** — `BuildTacticsBoardBenchCard` now computes `IsInjured` the same way the pin already does and shows `ManagerUITheme.BuildInjuryCrossIcon` in a reserved left gutter (same fixed-gutter approach `SquadListView` already uses, so the name doesn't shift row-to-row).
- **Condition color gradient on pins** — new `ManagerUITheme.ConditionGradientColor(float 0-100)`, a genuine green→yellow→red `Color.Lerp`, replacing the old 3-step `conditionColor` ternary. Also fixed a real gap while touching this: the border previously reflected only live in-match fatigue and was hardcoded flat green pre-match, so the season-long Condition system had zero visual presence before kickoff. Now blends both: persistent `ManagerSquadRoles.GetCondition` is always the base, and during a live match the worse of (persistent, live fatigue×100) wins — so a fatigued squad reads as such before a ball's kicked, and the border still visibly warms up as a match wears on, same as before.
- **Reserves/unavailable split** — `RefreshTacticsBoardUI`'s bench-building loop now partitions `team.Bench` into available vs. injured, renders available first, then an `"UNAVAILABLE (n)"` caption divider (new `BuildTacticsBoardBenchSectionCaption`) before the injured group — still built with the same `BuildTacticsBoardBenchCard` (injury cross included), still draggable, just visually separated from who's actually pickable.

**Live-verified** (temp test hook, real Play Mode): injured bench card's icon active, low-condition pin's border color measurably shifted from Accent, UNAVAILABLE caption appears when (and only when) there's an injured bench player. First pass on the condition-gradient check false-failed because it happened to grab `team.StartingEleven[0]` — conventionally the GK, whose fatigue is deliberately dampened 0.35x (session 13) — not a real bug, just the wrong player to stress-test with; fixed by excluding GK from the test's player pick.

## 4. Part 3: Per-match tactical override (new feature, not a bug fix)

Thomas's backlog ask: "formation/subs/mentality that apply to just the next fixture without changing the persistent Tactics default." Investigated first rather than building blind: **mentality already works this way** — `selectedMentality` resets to `Balanced` before every kickoff (`OnStartNewSeasonClicked`/`SimulateFixture`'s reset, confirmed by reading the existing code), so it was never persistent to begin with. The actual gap was formation + starting XI, which a Tactics Board edit mutates as the permanent default with no way to make it temporary.

**Design decision** (worth double-checking with Thomas): built as an **additive, opt-in toggle**, not a default-behavior change. A manager who never touches it gets the Tactics Board exactly as it's always worked — every edit is still the new permanent default. This was a deliberate choice over the alternative (auto-reverting every pre-match edit unless explicitly confirmed as the new default), which would have been simpler to build but risked surprising/annoying Thomas by changing the behavior of an already-shipped, actively-used screen without being asked.

- New `NEXT MATCH ONLY` button on the Tactics Board (hidden mid-match, same as Auto-Pick). Clicking it while off **arms** the override: snapshots `(team.Formation, team.StartingEleven)` into `nextMatchOverrideDefaultFormation`/`nextMatchOverrideDefaultStartingEleven`, highlights the button (reused `HighlightSelectedMentalityButton`). Any formation/lineup edit made afterward (formation switch, drag substitution, Auto-Pick) applies live to the real team as always — it's the *next matchday-advance* that's provisional, not the edit itself.
- New `ResolveNextMatchOnlyOverride`, called from both places `currentFixtureIndex` advances (the Simulate Season loop and `OnFullTimeContinueClicked`), same as the Inbox tick resolver — restores the snapshot via `AgentTeam.ChangeFormation` right after that one fixture's result has already been computed and applied, then clears the flag. Defensively filters the snapshot down to players still in `team.Players` and bails without touching anything if that leaves the XI short (a transfer/retirement landing in the exact one-fixture window between arming and resolving is a real if unlikely edge case).
- Clicking the button again while armed **cancels** rather than reverting immediately — whatever's currently set becomes the new permanent default, same as if the toggle had never been touched.
- Reset alongside every other session-scoped flag at season rollover and on load (a still-armed override has nothing left to revert to once the fixture list itself has changed).

**Live-verified** (temp test hook): arm → change formation → resolve one fixture → formation and XI both correctly reverted to the pre-arm snapshot; a second arm → change → *cancel* (not resolve) → a later resolve call correctly no-ops and leaves the cancelled state untouched.

## 5. Part 4: Two "real numbers" tests (both Thomas-requested, both ad hoc `Unity_RunCommand` measurements — no lasting code)

**Season-long OVR-movement count** (session 13's own open question: "are prime-age players actually static all season?"). Ran a full 38-fixture `OnSimulateSeasonClicked()` for Liverpool's real generated squad, diffing Overall before/after:

- **20/20 squad players moved Overall at all**, 20 moved ≥0.5, 16 moved ≥1.0. Average |delta| across the squad: **2.16**.
- By age bracket: Under-23 (n=5) avg |delta| 1.43. **Prime 23-28 (n=13) avg |delta| 2.44 — the highest of any bracket.** Veteran 29+ (n=2) avg |delta| 2.18.
- Biggest gain: +4.91 (age 28). Biggest loss: -2.16 (age 33).

**This refutes the session 13 finding, not confirms it.** The formula-reading conclusion ("a prime-age player gets no movement at all by design until a small random nudge at season rollover") was an overstatement of the real condition, which is `headroom > 0 AND age < GetGrowthEligibleUntilAge(player)` — not simply "age < 26". `GetGrowthEligibleUntilAge` is per-player (a base constant plus an individual aging-curve offset), and `headroom` depends on how close the player already is to their own Potential ceiling, not their age bracket alone. A real, realistically-generated Premier League-strength squad has plenty of prime-age players who haven't yet closed their headroom, and those grow every matchday same as anyone younger — confirmed directly, not inferred. The narrower "static" case the session 13 reasoning was actually describing only applies to a player who's *already* maxed their Potential but hasn't yet aged into decline — a real but much smaller slice than "prime-age players in general." No code change from this — it's a documentation correction, filed here and in memory so the next session doesn't re-open a question that's already been settled with real data.

**Standard match-sim regression check** (explicit end-of-session ask: "goals per match, table finishes, points, GD, all that jazz"), run the same way against the same simulated season — confirms this session's changes (all Manager-Mode UI/Inbox/data, nothing in `AgentMatchSimulator` or the ManagerSim fork) left match simulation untouched:

- 20 teams, avg **1.44 goals/team/match** (the trained statistical model's own weighted average was 1.45 — near-exact agreement). Zero rows with negative goals/points.
- Top: Manchester City, 77 pts, GD +40 (23W 8D 7L). Bottom: Burnley, 29 pts, GD -25 (4W 17D 17L). Every team played exactly 38 with W+D+L==Played.
- Managed team (Liverpool): 76 pts, GD +39 (21W 13D 4L), GF 67 GA 28 — a strong, plausible season.

## 6. Technique notes worth reusing

- **`Unity_RunCommand` scripts can't use `System.Reflection`** — the MCP sandbox rejects it outright ("unauthorized namespace"). The workaround already established in prior sessions (temporary public test-hook methods added directly to the source file, called by name, removed before handoff) is the only path for driving private controller state from outside Play Mode — confirmed again this session after a reflection-based first attempt failed immediately.
- **A test failure isn't always a real bug** — three separate false alarms this session, all from the test harness's own assumptions, not the code under test: (1) a post-match-reaction assertion checked the *last* message specifically, missed that a legitimate win-streak message was also firing on the same call; (2) a low-stamina test hammered condition down with only 2 calls, not enough to clear the threshold; (3) `team.StartingEleven[0]` (conventionally the GK) was used to stress-test the condition gradient, and GK fatigue is deliberately dampened 0.35x. Each time, re-reading the actual formula before assuming a code bug was the right call — worth the extra minute before touching "working" code.
- **Reuse existing helpers before writing new ones** — `GetOrdinalSuffix` already existed in the file; a first-pass addition duplicated it under the same name with a different signature and produced a genuine `CS0111` compile error, caught immediately via `Unity_GetConsoleLogs`.
