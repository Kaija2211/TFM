## 2. What happened this session

### A. Player realism

- **Age/Height added to `PlayerAgent`** (`Assets/Scripts/Sim/PlayerAgent.cs`) — new `Age`/`Height` fields, generated per-position (height) and via a bell-curve age roll in `AgentSquadGenerator.cs`, both coupled into existing attribute generation (height nudges Aerial/Strength/Pace, age nudges Composure/Positioning/Pace/Stamina down or up depending on youth/veteran). Height uses a Gaussian roll centered on a per-position band with a hard 150–200cm wall, not a uniform `Random.Range` clamp — the band is a center of gravity, not a limit (explicit user design preference, saved to memory as `feedback_generation_bell_curve_not_hard_range`).
- **Name pool expanded** (30/30 → ~84/81 diverse first/last names) and, more importantly, a real bug fixed: `usedNames` was a *local* `HashSet` inside `GenerateSquad`, so duplicate names were possible across different teams even before the pool was small (only de-duped within one team's own 20 players). Promoted to an instance field on `AgentSquadGenerator` so it's genuinely league-wide now. Verified: 400 generated players, 400 distinct names.
- **Attribute generation made realistic in both directions**, per explicit user request (his framing: a Ronald-Koeman-esque outlier should be *possible*, and "not a single real Premier League player would test at 6 in any stat"):
  - Every `Random.Range` stat roll in `ApplyBaseAttributes` and the ten `Generate<Position>` methods was converted to a Gaussian roll (`RollAttribute`, reusing `AgentSquadGenerator`'s own `RandomGaussian` helper) centered on the old range's midpoint, with the existing `ClampAttributes` 1–100 wall as the only true limit — same "bell curve not hard range" pattern as height.
  - ~18 "dump stat" floors that could roll into the single digits (e.g. a striker's Defending was 5–25, a GK's Finishing was 1–8) were raised to realistic pro-level floors (typically 18–25 minimum) — these were the actual source of the "6 in every stat" complaint, not the Gaussian conversion itself.
  - Verified across 6000 sampled attributes: only 0.05% fell below 10, and elite outliers above the old ceiling do occur (rare, ~0.3% in one stress test) without breaking typical distributions.

### C. Manager influence

This was a genuine back-and-forth design conversation, not a single feature request — the user explicitly wanted to *discuss* before building, per his own instruction from a previous session.

- **Formation fit-penalty** (`Assets/Scripts/Manager/ManagerFormationFit.cs`, new) — first finding from the discussion: formation was confirmed genuinely cosmetic (`Formation` never appeared in `AgentMatchSimulator.SimulateMatch` at all). `PlayerAgent.GetPositionFit()` already existed but was only used to rank candidates for the Squad UI's auto-fill-on-formation-change, never applied to real gameplay. Now: before every simulated match, a throwaway fit-penalized clone of each team's starting XI is built (every skill attribute scaled by `GetPositionFit()`), so playing someone out of position has a real mechanical cost. Never touches `SimulateMatch` itself or the real `PlayerAgent`/`AgentTeam` objects.
- **Tactics Board position-mismatch flagging**, refined twice this session:
  - First pass: pin's slot-position label turns red when the seated player's fit for that slot is below 0.85.
  - Second pass (explicit user request, later in the session): the mismatch color now shows the **player's true `PrimaryPosition`**, not the slot's position — so a misplaced ST at the DM spot shows red "ST", not red "DM", telling the manager exactly where the player belongs. Also added a **third tier**: positions "adjacent" to a player's primary (e.g. an LW at LM, even without LM as a rolled secondary) now get a lenient orange/`Warning` flag and a half penalty (fit 0.80) instead of the full red/0.60 penalty. The adjacency map (`PlayerAgent.AdjacentPositions`) deliberately mirrors the same position-family relationships `AgentSquadGenerator.AddSecondaryPositions` already uses for its own probabilistic secondary-position rolls, just made unconditional (doesn't require the dice roll to have actually granted that secondary) and fully symmetric.
  - Because `ManagerFormationFit` reads `GetPositionFit()` directly rather than a boolean threshold, extending the tiers automatically flowed through to the actual gameplay penalty too — no second place needed updating.
- **The ManagerSim fork** (`Assets/Scripts/ManagerSim/AgentMatchSimulator.cs`, new) — created because a "more match stats, without fabricating" discussion concluded that an honest Shots-on-Target stat needed a real on/off-target distinction in the sim, which the protected `Sim/AgentMatchSimulator.cs` can't take. The user's own suggestion: duplicate the protected files into a free-to-edit folder. Implementation: the fork is a byte-for-byte copy at creation time, declared `namespace Manager` (not a new namespace) with identical type names, so it shadows `Sim.AgentMatchSimulator` inside `ManagerPrototypeController.cs` (also `namespace Manager`, already `using Sim;`) via ordinary C# same-namespace resolution — zero call-site changes needed. `ResearchEvaluationRunner.cs` (`namespace Data`) is unaffected and still resolves to the real one. **Verified live, not just reasoned about**: a temporary marker string proved the fork is genuinely what Manager Mode runs, then removed. This pattern (and the guardrail clarification that it doesn't violate "don't touch the match simulator") is now documented in `PROJECT_CONTEXT_FOR_AI.md` section 6 and guardrail #12.
- **New match stats, all real/derived, none fabricated**: Possession% (share of attacking sequences per team — every event, not just shots, now carries `HomeTeamAttacking`), Chances Created (raw attacking-sequence count), Shots on Target (genuinely distinct from Shots now, via the fork's new off-target branch). Shipped in both the full-time report and — per explicit follow-up request — the live in-match stats ticker too.
- **Stamina/condition live indicator** (a CTO judgment call, not a specific user request) — Tactics Board pin borders now tint green/amber/red by live match fatigue, reading the exact same `GetFatigueMultiplier` the sim itself uses (made `public` in the fork for this).
- **"Tactic" renamed to "Mentality" throughout, and made genuinely live** — the user's own idea. Renamed `ManagerTactic`/`ManagerTacticModifier` → `ManagerMentality`/`ManagerMentalityModifier` (files, enum, every field/method/UI string), carefully preserving every unrelated "Tactics Board" reference (a completely different screen) untouched. More importantly: those three buttons were already visible/clickable live during a match but a code comment admitted they were "scaffolded... only affect the next match" — now a mid-match mentality change genuinely reruns the rest of that match via the same `TriggerMidMatchResimulation` path substitutions use. New `lastRawExpectedHomeGoals`/`AwayGoals` fields store the pre-mentality baseline so a second mid-match change recomputes cleanly instead of compounding modifiers. Caught and fixed a real ordering bug of my own here: inferring "is a match live" from panel visibility would have misfired during a *new* match's own setup; replaced with an explicit `isMatchCurrentlyLive` bool set only for the true duration of `ReplayMatchCoroutine`. ### D. Live bug-fix round

The user played the app live and reported four issues in one message. All four investigated and fixed in this same session, each verified against the actual running game, not just code review:

1. **Scroll direction (Match Events, Squad List)** — root-caused (empirically, via `ExecuteEvents`-simulated scroll + reading `Scrollbar`/`ScrollRect` state before and after) to `Scrollbar.direction = TopToBottom`, which is mismatched with `ScrollRect.verticalNormalizedPosition`'s own convention (1 = viewing the top of the content). This is a *different* bug from what a previous session already fixed and verified (`scrollSensitivity`, which governs wheel-to-content-movement and was already correct) — this one is specifically about the scrollbar *handle's* visual position. Fixed to `BottomToTop` in all three places it appeared, including the Tactics Board's bench rail, which had the identical mistake even though it wasn't reported.
2. **Pin-to-pin dragging** — pins could be dropped on (substitution) but not dragged themselves, so a formation change that scattered two players' slots couldn't be undone by dragging one back. Pins are now draggable too; `TacticsBoardPlayerCard.OnDrop` distinguishes a pin-origin drag (→ new `AgentTeam.SwapStartingPositions`, swaps two starters' slots, nobody touches the Bench, not logged as a substitution) from a bench-origin drag (existing substitute behavior).
3. **Match Log readability** — font 15→19, added line spacing.
4. **Stamina border staying stale after full-time** — confirmed a real bug, not by design: `currentMatchMinute` only resets at the *next* match's kickoff, so the Tactics Board kept reading late-match fatigue from the *previous* match right up until a new one started. Fixed by gating the condition calculation on the same `isMatchCurrentlyLive` flag added earlier in section C.

## 4. Gotchas learned this session (save yourself the rediscovery time)

- **`Scrollbar.direction` is a separate bug surface from `ScrollRect.scrollSensitivity`.** A previous session verified and fixed wheel-to-content-movement direction (`scrollSensitivity = 1f` is correct). This session found a *different* bug in the same visual area: `Scrollbar.direction = TopToBottom` renders the handle at the bottom of the track while viewing the top of the content (and vice versa) — backwards from user expectation. If a scroll complaint comes back again, check both independently; they're unrelated properties that happen to produce similar-sounding symptoms.
- **Reading a freshly-built `Scrollbar`/`ScrollRect`'s handle position via script immediately after navigation is unreliable.** Directly setting `.value` or `.verticalNormalizedPosition` doesn't synchronously recompute the handle's rendered size/position on a screen that hasn't run its own `Update`/`LateUpdate` cycle yet. Simulating a real scroll via `ExecuteEvents.Execute(..., ExecuteEvents.scrollHandler)` works, but even then, reading the result in the *same* synchronous `Unity_RunCommand` call can return stale handle-rect values — split into two separate tool calls (forcing a real frame boundary) for a reliable before/after read. Also: a `ScrollRect.content` can report `childCount=0`/`height=0` for a moment if you populate-then-immediately-inspect within one synchronous call chain (e.g. `OnSkipToResultsClicked()` followed immediately by `OnViewMatchEventsClicked()` in the same script) — the coroutine that actually finishes the transition needs a real frame to run first.
- **`OpenFootballMatch` is a `struct`, not a `class`** (`Assets/Scripts/Data/OpenFootballLoader.cs`) — `== null`/`!= null` comparisons against a `currentFixture`-typed field won't compile. Caught by the compiler immediately, but worth knowing before writing that check.
- **An explicit state flag beats inferring "is X currently happening" from panel/GameObject active-states**, when the two can be true independently even briefly. Found this the hard way while wiring live mentality changes: `SetMentality` is called both by real user clicks *and* internally during `OnSimulateMatchClicked`'s own setup (to re-highlight the footer pill) — at that second call site, panels can already look "live" by their active-state even though the replay coroutine hasn't reset per-match state yet. The fix (`isMatchCurrentlyLive`, true only for the literal duration of `ReplayMatchCoroutine`) then turned out to double as the fix for the separate stamina-staleness bug in section D — a single well-scoped flag solved two otherwise-unrelated-looking bugs.
- **`Time.timeScale` can be used to fast-forward a live match replay during testing** without touching any game logic — `ReplayMatchCoroutine`'s per-minute pacing is `Time.deltaTime`-accumulated against a fixed real-time target, so bumping `Time.timeScale` up (e.g. 25x) makes it finish in a couple of real seconds instead of ~45. Reset to `1f` afterward.
- **The ManagerSim fork pattern** (see section C and `PROJECT_CONTEXT_FOR_AI.md` section 6 / guardrail #12) — `Assets/Scripts/ManagerSim/AgentMatchSimulator.cs` is Manager Mode's own free-to-edit duplicate of the protected simulator, made to shadow the original via same-namespace C# resolution rather than needing any call-site changes. If a future feature needs real match-logic changes, check whether this fork already covers it before assuming the protected original needs touching.
- Carried forward, still true: `Destroy()` makes a `UnityEngine.Object` compare `== null` immediately despite deferred actual destruction; TMP mesh generation can silently fail on any label, destroy+recreate after a frame is the fix, but cache the *GameObject*/parent rather than the `TextMeshProUGUI` component itself if that label might get swept and recreated later (see section B's New Career subtitle bug); chrome-build-once (`Build*Chrome()` guarded by a bool) means neither code nor scene-file fixes apply to an already-running Play Mode session — always confirm with the user whether they've restarted since a fix landed; there is still no save/load system, so never restart Play Mode without checking whether the user has in-progress season state they care about first (this session, the user explicitly granted standing permission to restart Play Mode freely, but always still worth a quick check-in when there's visible progress on screen).
